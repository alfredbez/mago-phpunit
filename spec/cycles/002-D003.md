# Cycle 002: provider and dependency arguments

## Contract and scope

PHPUNIT-D003 covers positional data-provider rows combined with same-class
`#[Depends]` attributes. PHPUnit supplies the provider values first and then
dependency results in attribute order. `tests/runtime/ProviderDependsTest.php`
checks two provider values and two distinct dependency results. It also shows
that PHP accepts an additional argument beyond a user-defined method's declared
parameters. The extension's existing extra-provider-argument diagnostic is a
policy, not proof that PHP rejects every extra argument.

## Red and green

On PHP 8.4.27, PHPUnit 12.5.40 and Mago 1.58.2, the fixture and new assertions
in `tests/run.php` fail against the committed cycle 001 provider hook. It emits
five provider issues instead of three, including a missing-argument issue for
`testValid()`, which the runtime fixture executes successfully. The baseline
was tested in a disposable copy with only the hook restored to cycle 001.

The hook now subtracts the number of same-class `#[Depends]` attributes from
the required positional argument count, without moving the provider's type
checks or changing the existing extra-provider-argument rule. The suite passes
with three expected issues: too few provider arguments even after one dependency,
a wrong provider type, and too many provider arguments under the existing rule.
Without the extension, the provider issues are absent.

On PHP 8.4.27 the matrix passes PHPUnit 10.5.66, 11.5.57, 12.5.42 and 13.4.5.
Each ran 10 runtime tests and 25 assertions, the Mago fixture suite, and the
catalogue validator. These are four combinations, not proof for all supported
PHP versions. The separately locked PHPUnit 12.5.40 runtime also passed.

## Follow-up boundary

Named provider rows combined with dependencies behave differently by PHPUnit
major. `tests/runtime-negative/ProviderDependsNamedTest.php`, run separately,
passes on 10.5.66 but fails on 11.5.57, 12.5.42 and 13.4.5 with `Cannot use
positional argument after named argument during unpacking`. It is intentionally
outside the green runtime suite. The extension's existing named-row logic does
not account for dependencies, and this cycle does not claim to fix it. Neither
dependency clone/external attributes nor legacy dependency annotations are
counted; dependency-result types are not checked. Resolve these separately with
version-specific runtime evidence before extending the rule.
